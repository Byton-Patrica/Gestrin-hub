# 验收执行规范

量化门槛及版本完成定义见 [v0.1 规划](../V0.1-PLAN.md)。本页规定测试方法。

## 设备与运行器矩阵

五类分别建立手机、平板两个必测组合，至少一台 Adreno 设备和一台 Mali 设备进入整体测试集；候选运行器不支持的 GPU 组合记录为不支持并公开说明，不能写成通过。Android API 26 仅在 Hub 最低版本兼容性测试中使用；每个运行器组合须符合其自身最低要求。

每个组合固定 release 构建、设备型号/内存、Android 版本、SoC/GPU/驱动、运行器 APK 与游戏样例版本。所有报告初始为空；桌面构建或 UI 截图不能替代 Android 实测。样例使用自制、homebrew 或经授权内容，不把密钥和游戏文件提交仓库。

## 必测流程

首次导入 → 再次扫描去重 → 重启授权恢复 → 首次初始化 → 指定游戏冷启动 → 热启动 → 15 分钟交互 → 适用的保存/恢复 → 返回记录。另测缺少运行器、未知版本、错误格式、撤销授权、删除来源、进程回收和取消扫描。

升级测试保留至少一份旧数据库样例，验证游戏编辑、收藏、URI 和运行器绑定可迁移；运行器升级后对入口、URI 和前置条件重新回归。

## 性能与诊断

使用固定的 1,000 条元数据库，搜索采样至少 50 次，冷启动至少 20 次，滚动录制至少 3 段固定手势；记录工具、构建类型、温度/省电状态和 p95。游戏运行帧率与 Hub 界面性能分别统计。

诊断使用有已知原因的脱敏日志集，覆盖正常日志、未知错误、截断文件与包含诱导命令的内容。建议必须引用输入证据；未知原因不得编造修复。模型缺失、取消、内存不足与超时均回退规则结果，不影响游戏库。

## 发布证据

每类至少一份完整探针记录，加手机/平板测试报告、关键失败截图或日志、性能记录、许可证清单和已知限制。缺失证据的项目保持未验证；任何例外都在版本说明中列出，不能无声降低 v0.1 的五类支持目标。
